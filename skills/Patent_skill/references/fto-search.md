# FTO 防侵权检索模块

本模块把一个技术方案转成可复核的 FTO 初筛计划。它复刻的是“输入技术方案 → 提取技术特征 → 扩展关键词 → 扩展 IPC/CPC → 多轮组合检索 → 候选专利初筛 → 权利要求要素比对”的工作流，不复制商业数据库的排序算法，也不输出侵权或不侵权的法律结论。

## 何时使用

当用户给出一段拟实施方案、产品说明、治疗流程、检测流程或组合治疗方案，并要求“防侵权检索、FTO 初筛、找相关专利、对比技术特征”时，读取本文件并运行：

```text
scripts/build_fto_plan.py       # 生成特征、扩词、分类号和检索轮次
scripts/score_fto_candidates.py # 对已有权利要求要素做可解释的候选排序
scripts/build_fto_dashboard.py  # 生成类似产品工作流的可交互 HTML
```

## 输入与输出

案例目录可包含 `fto-input.json`。最小输入结构为：

```json
{
  "technical_solution": "拟实施技术方案",
  "features": [
    {
      "id": "F01",
      "feature_type": "core",
      "importance": "core",
      "text": "技术特征描述",
      "keyword_clusters": ["drug", "target"],
      "classifications": ["A61K39/395"]
    }
  ],
  "keyword_clusters": [
    {
      "id": "drug",
      "label": "药物",
      "base_terms": ["度伐利尤单抗", "durvalumab"],
      "expanded_terms": ["Imfinzi", "MEDI4736"]
    }
  ]
}
```

`build_fto_plan.py` 会生成：

- `fto-search-plan.json`：机器可读的特征、词簇、IPC/CPC、检索式、初筛规则和缺口；
- `fto-search-plan.md`：可读的 FTO 检索计划；
- `fto-search.html`：阶段式交互页面，包含技术特征、扩词、分类号、检索轮次和候选专利表。
- `source_catalog`：从 [patent-database-sources.json](patent-database-sources.json) 注入 CNIPA/PatentDatabases 来源目录；当前快照包含 143 条上游记录、140 个去重 URL，并按国内、国外、分类号工具以及官方/聚合/上下文用途标注。

若没有 `fto-input.json`，脚本会用 `research_scope.json` 和 `identity.json` 生成保守的基础计划，但不能替代人工拆分技术方案。

## 技术特征提取原则

先把方案拆成“对象、机制、步骤、检测指标、结果/阈值、给药/剂量、患者人群、分类号”八类要素，再标注：

- `core`：不包含它就不是同一技术方案的核心特征；
- `necessary`：目标实施通常需要，但可能不是每个权利要求都限定；
- `support`：用于提高召回率或识别从属权利要求；
- `context`：技术领域和背景词，仅用于定位，不能单独作为侵权判断要素。

关键词扩展要区分：同义词、旧名/研发代号、缩写、上下位概念、机制词、临床表达和检测表达。扩展词是检索工具，不是技术事实；每个词簇要记录来源和关联特征。

IPC/CPC 扩展要先从高相关专利或官方分类定义反向确认，再加入检索式。分类号适合提高召回和识别邻近技术，不能单独证明权利要求覆盖。

## 检索轮次

默认按以下顺序生成检索轮次：

1. **R1 精确组合**：药物/靶点/适应症/风险或检测词；
2. **R2 机制扩展**：药物 + 通路/结合/阻断 + 不良事件或器官损伤；
3. **R3 器官与症状**：肺炎、肠炎、内分泌、肝肾损伤等具体事件 + 监测词；
4. **R4 检测与指标**：生化指标、影像、阈值、分级、连续监测；
5. **R5 干预与处置**：治疗期间、分级、激素/皮质类固醇、暂停或恢复给药；
6. **R6 分类号检索**：IPC/CPC 与核心机制/检测词组合；
7. **R7 关系扩展**：申请人、引用、同族、分案/继续申请和邻近方案。

每轮检索都要记录数据库、字段、式子、日期、结果数量、纳入/边界/排除决定和来源 URL。检索结果的“相关性”只用于排序；最终判断必须回到目标法域的权利要求和官方状态。

## 来源目录与路由

本 Skill 使用 CNIPA/PatentDatabases 作为“来源发现目录”，而不是把目录中的每个网站都视为同等证据。运行 `scripts/update_source_registry.py` 可以从上游 README 刷新目录快照；脚本保留来源名称、URL、上游分组、来源角色、默认用途和上游 README 哈希。

按以下路由使用：

- `primary_or_status_check`：目标法域官方公开、审查、登记簿或国家阶段系统。用于核验公开文本、审查事件和法律状态；不能用别的数据库标签替代。
- `discovery_and_cross_check`：商业数据库、聚合平台、公共镜像和国家/地区检索入口。用于扩大召回、同族、引证、申请人和全文交叉核对；需要记录访问日期和覆盖限制。
- `context_only`：PubMed、CNKI、万方、NSTL 等文献/情报入口。用于技术、临床和背景语境，不证明专利权利要求覆盖。
- `classification_navigation`：IPC/CPC/FI/ECLA/ICO 分类导航和对照工具。用于分类解释与扩展，并记录分类版本或页面日期。

来源选择不是“全部自动抓取”。对于需要注册、验证码、订阅、人工操作、无法检全库、仅显示著录项或链接已失效的来源，标记为 `pending/manual`，不要伪造结果数量。商业数据库的字段加工和智能排序也不能被当作本 Skill 的算法或官方事实。

来源目录中的每条来源都应写入 `source-log.jsonl`；可使用 `scripts/append_source_log.py --source-id <source_id>` 记录来源目录 ID，形成“检索式—来源—结果—证据”的可追溯链。

## 初筛与比对

候选排序可以使用透明的加权信号：

- 核心特征命中权重最高；
- 必要特征和权利要求类别（用途、组合、检测、制剂、给药方案）次之；
- 支撑特征、分类号和摘要命中用于召回；
- 公开镜像的状态只能作为筛选信号，官方登记簿状态优先。

输出中应显示“命中的特征、命中词、权利要求类别、状态信号和缺口”，不要只给一个黑盒相似度分数。缺少独立权利要求、法域成员或官方状态时，标为“待复核”。

## 法律边界

FTO 初筛回答的是“哪些公开专利族值得进一步核验”，不是“必然侵权”。必须把：

1. 权利要求保护范围；
2. 目标法域的成员、分案/继续申请；
3. 截止日期的有效性与法律事件；
4. 实施方案与全部权利要求要素的对应关系；

分开记录。涉及商业实施、上市或诉讼时，应由专利律师基于官方登记簿、审查档案和完整 claim chart 复核。
